feat(security): OTP-gate the admin email change, closing the takeover path

schools.email IS the admin login identifier -- admin_auth matches on it.
Accepting a bare {"email": "..."} on the profile route means anyone who
reaches that form (unattended session, shared office machine, CSRF'd tab)
can silently redirect the school's account to a mailbox they control, and
the takeover stays invisible until the real owner cannot sign in.

The proof is now POSSESSION OF THE NEW MAILBOX, not an authenticated
session, because a session can be borrowed.

* email_change joins the OTP purpose allow-list. Purpose is part of the
  store's lookup key on BOTH issue and consume, so a code minted during
  registration cannot authorise an account change weeks later, and a
  change code cannot be replayed at signup.

* The Next OTP proxies forward purpose instead of hardcoding
  'registration'. Hardcoding would have made email_change unrequestable
  through them entirely.

* The profile route returns 428 when an email change arrives without
  proof, re-consumes the code server-side on the write, and returns 403
  when the code is bad. otp_verified alone is not trusted -- a client
  sending otp_verified=true with no real code still fails.

* UNCHANGED email skips the gate entirely, so editing the motto never
  demands a code.

* The demo tenant is exempt so the sample school stays editable, keyed off
  subscription_status rather than the hostname, so it travels with the
  registry row instead of a URL.

* otp fields are forwarded by the settings proxy OUTSIDE the profile
  column allow-list: they are evidence, not data, and keeping them out
  stops a future widening of that list persisting them into schools.

* After a successful change the admin is bounced to login, because the
  session this page rendered under was keyed to an identifier that no
  longer exists.

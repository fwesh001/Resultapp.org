fix(rbac): enforce capability at page + proxy, not in the layout

Step 2 of the Moderator RBAC work. The important part of this commit is
what it does NOT do, and why.

Next 16 does not expose a child page's exports to its parent layout, so
`(children as {requiredCapability}).requiredCapability` is `undefined`
for every page. I attempted exactly that and proved it failed before
shipping: a temporary probe in the layout logged
`requiredCapability=undefined` for two different pages against a real dev
server. Had it gone out, the guard would have silently never fired, every
moderator would have had full admin access, and every test would still
have been green.

So the gate moved to the two places that CAN see the route:

  * every admin page calls enforceAdminCapability(params, "<cap>")
    (lib/enforceCapability.ts)
  * every app/api/admin/* proxy calls requireAdminCapability()

and the sidebar hides what the server would refuse, which is UX so a
moderator does not click through to a 403.

Capabilities are an allow-list, not a deny-list. A page added tomorrow is
inaccessible to moderators until someone grants it, rather than silently
reachable. `notifications` went to admin-only: that portal is where
announcements are authored for every parent and staff member.

Session claims gain `role` and `capabilities`, minted only in the login
proxy. Sessions from before RBAC carry neither and are treated as the
plain admin -- revoking access from someone who already has it is the
safe direction for a boolean guard.

X-Viewer-Role / X-Viewer-Id / X-Viewer-Label / X-Viewer-Caps now ride
along on admin proxy calls. This is defence in depth, not a hard
guarantee, and the header block says so: the backend already accepts the
shared secret alone, so the same secret that forges these headers already
grants full access. The real guarantee stays in Next, on the request, in
a place the caller cannot touch.

The export proxy now also requires the `export` capability rather than
any signed session.

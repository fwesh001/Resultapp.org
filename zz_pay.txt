feat(payments): canonical Flutterwave keys, fail-closed, webhook safety net

KEY HANDLING
------------
Each setting now has EXACTLY ONE env name. The previous chains
(FLW_SECRET_KEY, FLW_SECRET_HASH, NEXT_PUBLIC_FLW_PUBLIC_KEY,
NEXT_PUBLIC_FLUTTERWAVE_PUBLIC_KEY_TEST, FLUTTERWAVE_WEBHOOK_HASH) are gone.

That chain is why a live secret sat in .env under an unrecognised name while
the TEST key carried on serving production, and why the webhook checked
FLUTTERWAVE_WEBHOOK_HASH (absent everywhere) before the one that was actually
set. An alias chain is a way of losing configuration without noticing.

Both public-key call sites previously fell back to a hardcoded
FLWPUBK_TEST-dummy-... when the real key was missing. A misnamed or unset live
key therefore opened a completely normal-looking TEST checkout: the operator
saw a working pay button, the school saw a payment form, and no money moved.
Both now throw, and the error surfaces to the user as an explicit
"payments are unavailable". A missing key is a deployment error, not a mode.

DEMO
----
The demo advertises a test card, which a live key rejects outright, so it gets
a dedicated NEXT_PUBLIC_FLUTTERWAVE_DEMO_PUBLIC_KEY selected by the registry's
own demo flag. It is a SEPARATE variable rather than a fallback, because a
fallback is the exact failure being removed. Real tenants cannot reach it: the
choice is made server-side from subscription_status, never the hostname.

WEBHOOK — the paid-but-never-provisioned gap
--------------------------------------------
The webhook verified its signature and then only console.log'd. Registration
provisioned solely from the browser callback, so a closed tab, a crash or a
dead connection after settlement left a school having paid for a portal that
did not exist.

It could not simply be fixed in the webhook, because the admin password is
DELIBERATELY absent from the checkout meta — Flutterwave retains transaction
metadata, and putting a credential there would disclose it to a third party
(a remediated P0, not being revisited). So the details are now parked
server-side BEFORE checkout opens:

  pending_registrations table  (short TTL, deleted on success)
  lib/pendingRegistrationCrypto  AES-256-GCM under a DEDICATED key
  lib/pendingRegistrations  hold / claim / provision, shared by both paths
  POST /api/register-school/hold

PENDING_REGISTRATION_SECRET is separate from SESSION_SECRET on purpose: reusing
it would merge "can forge a session" and "can read a parked password" into one
compromise surface.

Idempotency rests on an atomic claim (pending -> completed WHERE still
pending). Both paths run identical logic, so whoever claims first provisions and
the other exits. A 409 from the backend means "the other path already finished",
which is logged as success rather than as an incident. A failed provision
RELEASES the claim so a retry can proceed — otherwise a transient outage would
strand a paid customer permanently.

The webhook re-verifies the transaction against Flutterwave's API rather than
trusting its own payload, so both paths derive amount/status/currency from the
same authoritative source and neither can be talked into provisioning an unpaid
school.

Signature checking now uses timingSafeEqual and refuses when the hash is unset.
The previous version returned NODE_ENV !== "production" in that case, meaning a
missing variable silently ACCEPTED every webhook in development — exactly where
you would rehearse an attack and believe it was rejected.

feat(ui): accessible InfoTooltip, piloted on Billing and Settings

The helper copy this replaces was permanent small text under every field.
That is fine on desktop and actively harmful on mobile, where a screen of
form is mostly secondary explanation and the real inputs sit below the fold.

A tooltip is the rare component that is genuinely two different controls.
Desktop hover works because a pointer is non-committal: moving over
something is a question, not an answer. Touch has no hover, and `:hover`
latches open on tap with no way out — worse, the first tap can be swallowed
trying to open it, so the control reads as broken.

So the two paths are bound to `(pointer: coarse)` rather than to `:hover`:
fine pointers get hover and focus, coarse pointers get tap-to-toggle plus
an explicit close button, because a touch device has neither hover nor an
Escape key. A hybrid laptop reports `pointer: fine` AND has a touchscreen,
which is exactly why matching on `hover: hover` would have been wrong.

Keyboard bindings are bound to key events instead, so both paths stay live
at once — pointer type is a statement about the primary pointer, not a
promise that nobody is using a keyboard.

The panel is a live region rather than aria-describedby alone: a tooltip
that was never focused is silent to a screen reader, so the explanation
would simply not be announced. It does not trap focus and closes on Escape,
matching APG's non-modal dialog pattern — a help bubble is not a modal, and
someone who opened it should be able to keep tabbing through the form.

Pilots: the slots-vs-credits distinction and the per-credit charging rule on
Billing, and the admin-login-email warning on Settings.

Also unwrapped Billing's double gutter: it had min-h-screen inside a
<main> that is already flex-1 overflow-y-auto, so the inner column was
viewport-tall inside a viewport-tall box, and page padding was applied
twice. Verified in Chrome at 375px: wrapper min-height now 0px, single
24px gutter, no horizontal overflow.
